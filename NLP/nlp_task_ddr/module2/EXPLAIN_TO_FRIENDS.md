### A plain-English guide for presenting to teammates

## The Big Picture First

Imagine you are an oil company drilling a new well somewhere in the North Sea.
Drilling is dangerous — you can lose mud into cracks in the rock, your pipe can
get stuck, you can accidentally hit a high-pressure zone and cause a "kick" (the
start of a blowout).

The whole NWIS-Sentinel project answers one question:
> **"What happened to OTHER wells near mine that faced the same geological
> conditions — and what can I learn from their mistakes?"**

The 4-module project is split across 4 people (P1 → P2 → P3 → P4).
**We are P2.** Our job is to take the raw data P1 gave us and build:
1. An **interactive map** that shows all 159 wells
2. A **similarity engine** that ranks which historical wells are most
   "analogous" to a target well, separately for each type of drilling hazard

## Part 1 — What We Built: The Interactive Map

### File: `module2/templates/map.html` + `module2/app.py`

### Why we built it
The official SIH requirement explicitly says:
> "Interactive map-based visualization, user-defined radius"

Engineers in the field need to visually see where nearby wells are,
and they need to be able to draw a circle and say "show me all wells
within 100 km of mine."

### How to open it
```
Run:   python module2/app.py
Open:  http://localhost:5001
```

### What you see when you open it

**The Map (right side)**
- A dark North Sea map with 159 colored dots (wells)
- Blue dots = FORCE 2020 real wells
- Orange dots = Volve real wells
- Red dots = Synthetic wells
- The colors are always visible so you always know which data is real vs fake
  (this is a hard requirement from the project rules — no hidden synthetic data)

**The Sidebar (left side)**
Has 5 sections:

1. **Well Sources legend** — explains what each color means

2. **Select Well dropdown** — pick any of 159 wells by name

3. **Search Radius slider** — drag from 5 km to 300 km.
   When you set this, a dashed circle appears around your selected well
   and all wells inside that circle turn YELLOW ("in radius").
   The counter shows how many are inside.

4. **Hazard Similarity View pills** — 5 buttons:
   Mud Loss | Stuck Pipe | Overpressure | Torque Spike | Cementing
   Click one to see which wells are most similar for THAT specific hazard.

5. **The Analog Panel** — when you select a well, this fills with:
   - The selected well's details (depth, BHA type, known hazard events)
   - The AHP weights being used for the selected hazard
   - Top 8 most similar "analog" wells with score breakdown bars

### How the map actually works (technical)
- Flask (Python web server) runs on port 5001
- When the browser opens, it calls `GET /api/wells` → gets all 159 wells as JSON
- Leaflet.js (a free mapping library) plots each well as a circle marker
- When you select a well, the browser calls `GET /api/analogs?well_id=X&hazard=Y`
  → gets the ranked list of similar wells → displays them in the sidebar
- OpenStreetMap/CARTO provides the map tiles (free, no API key needed)

## Part 2 — What We Built: The Similarity Engine

### File: `module2/compute_similarity.py`

This is the most technically interesting part. Let me explain it like a story.

### The Problem We Are Solving

Suppose you are drilling Well A and you are worried about STUCK PIPE.
You want to know: "Which of the 158 other wells in our database was
MOST SIMILAR to mine, specifically in the factors that cause stuck pipe?"

A naive answer would be: "Just find the nearest well geographically."
But that is wrong — a well 200 km away that has the exact same wellbore
trajectory, BHA, and formation might be far more relevant than a nearby well
drilled in completely different conditions.

We need HAZARD-SPECIFIC similarity. The factors that make two wells
"similar" for stuck-pipe risk are completely different from the factors
that make them similar for mud-loss risk.

### The 5 Hazard Types and Their Key Factors

| Hazard | The Main Question | Dominant Feature |
|---|---|---|
| **Mud Loss** | Does the rock have the same fractures/porosity? | Formation type (49.7%) |
| **Stuck Pipe** | Does the wellbore have the same shape? | Trajectory curve (49.7%) |
| **Overpressure** | Is the mud heavy enough for the pore pressure? | Mud weight (52.1%) |
| **Torque Spike** | Does the well path create the same drag? | Trajectory curve (44.8%) |
| **Cementing Issue** | Is the same type of mud contaminating the cement? | Mud type (49.7%) |

### The Similarity Formula

For each pair of wells, we compute 5 individual similarity scores (all between 0 and 1):

**1. Formation Similarity (Jaccard)**
We look at the list of rock formations each well drilled through.
- Well A drilled through: {Aasgard, Sola, Bryne}
- Well B drilled through: {Aasgard, Sola, Ekofisk}
- Overlap = {Aasgard, Sola} = 2 formations in common
- Union = {Aasgard, Sola, Bryne, Ekofisk} = 4 total
- Jaccard score = 2/4 = 0.50 (50% similar in formations)

**2. Mud Weight Similarity (Gaussian Kernel)**
- We take the average mud weight (in ppg) used in each well from the events data
- Well A average: 12.5 ppg, Well B average: 12.8 ppg
- The closer they are, the higher the score
- Uses a Gaussian (bell curve) formula so small differences barely matter,
  large differences strongly penalize the score
- If no mud weight data exists for a well, we give it 0.5 (neutral score)

**3. BHA Type Similarity (Jaccard on words)**
- BHA = Bottom Hole Assembly (the drill bit + tools at the bottom of the drill string)
- We tokenize the BHA description into words
- Example: "PDC Rotary Steerable Assembly" → {PDC, Rotary, Steerable, Assembly}
- Same Jaccard overlap as formations

**4. Mud Type Similarity (Jaccard on words)**
- We tokenize the mud system description
- Example: "KCl/Polymer WBM" → {KCl, Polymer, WBM}
- Oil-Based Mud (OBM) vs Water-Based Mud (WBM) wells will score low similarity

**5. Trajectory Similarity (Dynamic Time Warping)**
- Each well has a trajectory: a list of (measured depth, inclination angle) points
- This is the shape of the wellbore — is it mostly vertical? Does it deviate a lot?
- We use Dynamic Time Warping (DTW) to compare these curves
  even if they have different numbers of points or different depths
- DTW is the same algorithm used to compare speech patterns or stock price curves
- We use the `fastdtw` library which is O(N) — fast even for long sequences
- Result is converted to a 0-1 similarity score (higher = more similar shape)

**Then we combine them with AHP weights:**
```
Final Score = w1×formation + w2×mud_weight + w3×BHA + w4×mud_type + w5×trajectory
```
where the weights depend on which hazard you are analyzing.

### What is AHP and Why Did We Use It?

AHP = **Analytic Hierarchy Process** (invented by Thomas Saaty, 1977).
It is a standard operations-research method for deriving weights when you
have multiple criteria and want to be mathematically rigorous and transparent.

**How AHP works:**
1. You create a matrix comparing every feature against every other feature
   pairwise. For stuck pipe, you say: "How much more important is trajectory
   than formation? About 7 times more important."
2. You fill in all pairs (5 features = 5×5 matrix = 25 comparisons, but only
   10 unique pairs because the matrix is symmetric)
3. You compute the principal eigenvector of that matrix → these are your weights
4. You compute a Consistency Ratio (CR) to check if your comparisons make
   mathematical sense (CR < 0.10 = acceptable)

**Our AHP results — all 5 hazards passed (CR < 0.10):**

| Hazard | formation | mud_weight | bha_type | mud_type | trajectory | CR |
|---|---|---|---|---|---|---|
| mud_loss | **49.7%** | 24.5% | 10.5% | 10.5% | 4.7% | 0.028 ✅ |
| stuck_pipe | 4.7% | 10.5% | 24.5% | 10.5% | **49.7%** | 0.028 ✅ |
| overpressure | 28.3% | **52.1%** | 7.9% | 7.9% | 3.7% | 0.041 ✅ |
| torque_spike | 5.4% | 12.5% | 26.2% | 11.2% | **44.8%** | 0.048 ✅ |
| cementing | 24.5% | 10.5% | 10.5% | **49.7%** | 4.7% | 0.028 ✅ |

The percentages show how much each feature contributes to the final score.
For mud loss, 49.7% of the score comes from formation overlap — because
the rock type is the biggest determinant of mud loss risk.
For stuck pipe, 49.7% comes from trajectory shape — because the wellbore
geometry is what causes the pipe to get stuck.

### What the Engine Computes

- 159 wells × 158 comparisons × 5 hazards = **125,610 similarity scores**
- Each score stores: the final weighted score + all 5 individual feature scores
  + the exact AHP weights used → full transparency, no black boxes
- Takes ~2 minutes to compute
- Saved to `module2/outputs/analog_wells.json` (75 MB)

## Part 3 — The 3 Output Files We Hand to P3

### File 1: `analog_wells.json` (75 MB) — THE MAIN DELIVERABLE

Structure (simplified):
```
For every well X:
  For every hazard H (mud_loss / stuck_pipe / overpressure / torque_spike / cementing):
    Sorted list of the 158 other wells, from most similar to least similar
    Each entry includes:
      - weighted_score (0 to 1) — the final similarity score
      - feature_breakdown — the 5 individual scores that made up the total
      - ahp_weights_used — the exact weights applied (full audit trail)
      - is_synthetic flag — always shows if the analog is real or fake
```

**P3 uses this to:** When a well is actively drilling and showing early warning
signs of stuck pipe, P3 finds the top analog wells from this file, looks up
their historical event sequences, and predicts "these wells got stuck at
similar conditions — here is what happened next."

### File 2: `ahp_weights.json` — FULL AUDIT TRAIL

Contains the complete pairwise comparison matrices and the derived weights
for all 5 hazards. Any reviewer can open this file and verify exactly why
formation got 49.7% weight for mud loss — the raw matrix is right there.
This satisfies the project's "No Black Boxes" rule.

### File 3: `formation_correlation.json` — CROSS-WELL FORMATION TABLE

For each of the 59 unique formations in the dataset, lists every well
that drilled through it, at what depth, with GPS coordinates.
Example: "Aasgard Formation" → drilled by 53 wells, at depths ranging
from 755m to 4374m across the Norwegian shelf.
P3 and P4 use this to show: "When you are drilling through the Aasgard
formation at 2500m, these 12 other wells experienced X hazard here."

## Part 4 — The Bug We Fixed

During testing, clicking any well with a "/" in its name (like `16/4-1`,
`15/9-F-9A`, `7/1-1`) caused the sidebar to show:
> Error: Failed to execute 'json' on 'Response': Unexpected token '<'

**Root cause:** Well IDs like `16/4-1` contain a slash. When the JavaScript
called `/api/well/16%2F4-1`, Flask saw the `%2F` (encoded slash) as a
real URL path separator, tried to find a route for `/api/well/16/4-1`
(which does not exist), and returned a 404 HTML error page.
JavaScript tried to parse that HTML as JSON and crashed on the `<` character.

**Fix (2 lines changed):**
- `app.py`: Added `@app.route('/api/well')` accepting `?well_id=` as a query parameter
- `map.html` line 422: Changed fetch call from `/api/well/${id}` to `/api/well?well_id=${id}`

After fix, all 4 problem wells passed: `16/4-1`, `15/9-F-9A`, `7/1-1`, `34/3-2 S`.

## Part 7 — What P3 Needs to Do Next

P3 reads `README_module2_geospatial_and_similarity.md` first.
Then P3:
1. Loads `analog_wells.json` → takes the top-K analog wells per hazard
2. Looks up those analogs in P1's `events.jsonl` → gets their historical event sequences
3. Uses sequence alignment (Needleman-Wunsch algorithm) to match the
   live drilling event sequence against those historical sequences
4. Reports: "Your current sequence matches 3 of 5 analogs that then experienced
   stuck pipe (60%, Wilson 95% CI: 23%-88%)"
5. Performs the "time-travel backtest" — replays a real historical incident
   through the pipeline and proves the system would have warned early

P3 does NOT need to rerun our compute_similarity.py — the outputs are ready.
P3 only needs `analog_wells.json`, `ahp_weights.json`, and P1's event files.
